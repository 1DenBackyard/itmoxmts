# ТЗ: прототип системы анализа документации объектов данных (Streamlit)

**Статус:** итоговое ТЗ для прототипа (handoff бэкенду / ML)  
**Роль заказчика документа:** Product Manager  
**Стек прототипа:** Streamlit (UI) + заглушка / лёгкая LLM + mock multi-agent  
**Вне скоупа прототипа:** продакшен-инфра, тонкая настройка моделей, особенности команд-потребителей ТЗ  

---

## 1. Цель и контекст

Разработать **прототип UI + контрактов**, который:

1. От лица аналитика / разработчика / тестировщика анализирует документацию объектов данных.
2. Указывает места, которые нужно **дополнить / скорректировать**.
3. Категоризирует замечания по **рискованности** (светофор + «прожарка»).
4. Помогает исправлять через подсказки (проблема → вопросы → рекомендация).
5. Собирает **самообучение аналитика** только по реально принятым правкам.
6. Уходит бэкендерам как эталон экранов, UX-потоков и JSON-контрактов.

Система целевая — **мультиагентная**; в прототипе агенты и модели **эмулируются** (лёгкая модель или rule/mock). Финальная настройка моделей — зона ответственности отдельного участника команды.

Данные в датасете **обезличены**.

---

## 2. Пользователи и роли (прототип)

| Роль в UI | Назначение |
|-----------|------------|
| Аналитик | Основной пользователь: загружает ТЗ, смотрит замечания, правит, отмечает «исправлено» |
| Разработчик / тестировщик | Переключатель «точки зрения» агента-ревьюера (влияет на фокус замечаний) |
| PM / тимлид (опционально) | Смотрит дашборд самообучения |

В прототипе достаточно одного пользователя с выбором роли ревьюера. Авторизация не обязательна.

---

## 3. Входные данные (датасет)

Папка: `ДатасетТЗ/`

| Файл | Назначение |
|------|------------|
| `Шаблоны документации.pdf` | Эталон структуры разделов документации |
| `Тестовые данные для Хакатона-2-4.pdf` | Пример: описание потоков данных (геолокация) |
| `Тестовые данные для Хакатона-5-6.pdf` | Пример: описание данных системы-источника (CDR / prepaid) |
| `Тестовые данные для Хакатона-7-9.pdf` | Пример: описание витрины-агрегата (`TABLE_AGG_DEVICES`) |

**Приёмочный сценарий алгоритма:** новый документ типа «витрина-агрегат» (по аналогии с 7–9).

### 3.1. Типы документов

1. Описание потоков данных / витрин.
2. Описание данных системы-источника.
3. Описание витрины-агрегата.

### 3.2. Опорные разделы шаблона (чеклист полноты)

Прототип должен уметь маппить замечания на блоки шаблона, в т.ч.:

- Общие сведения, решаемая проблема, продуктовые метрики, заказчики  
- Нефункциональные требования (объём, задержки и т.п.)  
- Системы-источники, Data Catalog, исходники (GitLab), команда, JIRA  
- Источники данных / обогащения, приёмники (кластер, каталог, сериализация)  
- Схема потоков данных  
- Алгоритм обработки: фильтрация, обогащение, преобразования, ключ/партиция  
- Структура данных (поля, типы, описание, логика расчёта)  
- Пример данных, DDL, FAQ, история изменений

## 4. Фокус качества анализа (must)

Система в первую очередь ищет пробелы и несостыковки по:

1. **Расположение источников и Kafka-кластеров**  
   (топики, регионы, кластер, схема, путь/приёмник, retention и т.п.)
2. **Поля и логика их расчёта**  
   (формулы, join’ы, fallback, источники атрибутов)
3. **Фильтрация данных**  
   (условия, окна времени, исключения)
4. **Обновление и объём данных**  
   (регламент, инкремент/полная перезагрузка, глубина истории, объёмы/latency)

Дополнительно (желательно): противоречия между блоками одного документа, пустые обязательные секции шаблона, «заглушки» без конкретики.

## 5. Метрика приоритизации замечаний

Для каждого замечания ИИ считает:

```
score = P(проблема) × Impact
```

где:

- **P(проблема)** ∈ [0..1] — вероятность, что раздел реально проблемный / приведёт к ошибке внедрения  
- **Impact** ∈ [0..1] — влияние на разработку / тестирование / бизнес-использование данных  

Округление и шкалы в прототипе можно упростить (например, Impact = {0.3, 0.6, 1.0}).

### 5.1. Светофор + «прожарка»

Все замечания **показываются**, но категоризируются:

| Score (ориентир) | Светофор | Прожарка (UX-лейбл) | Смысл для аналитика |
|------------------|----------|---------------------|---------------------|
| ≥ 0.75 | 🔴 красный | **Well done** | Критично: без правки высокий риск срыва / неверной витрины |
| 0.45–0.74 | 🟠 оранжевый | **Medium** | Важно: лучше исправить до передачи в разработку |
| 0.25–0.44 | 🟡 жёлтый | **Medium rare** | Желательно уточнить; можно отложить |
| < 0.25 | 🟢 зелёный | **Rare** | Низкий риск / косметика / стиль |

> Названия прожарки фиксируем в UI как бренд фичи («Прожарка замечаний»). Альтернативные формулировки не плодим.

Фильтры на странице документа: по прожарке, по блоку шаблона, по роли ревьюера, по статусу (новое / в работе / исправлено / отклонено).

---

## 6. Формат подсказки по замечанию («карточка правки»)

Каждая карточка обязана содержать:

1. **Проблема**  
   Кратко, что не так (например: «Несостыковка между блоками»; «Не описан Kafka-топик для региона Sib»; «Нет логики расчёта поля X»).
2. **Вопросы для самостоятельной правки**  
   2–5 наводящих вопросов, чтобы аналитик сам додумал и заполнил.
3. **Конкретная рекомендация**  
   По возможности вида: «Исправь на “X”» / «Добавь в раздел Y таблицу Z с полями…».  
   Если точный текст неизвестен — явная формулировка «уточни у владельца источника» + что именно спросить.
4. **Метаданные**  
   - блок документа / якорь (заголовок, страница/фрагмент)  
   - P, Impact, score, прожарка, светофор  
   - роль агента, тип документа  
   - статус карточки  

Опционально в прототипе: цитата фрагмента документа («evidence»).

## 7. Интерфейс: 2 страницы

### Страница 1 — Работа с документом

**Цель:** загрузить ТЗ → получить разбор → пройтись по замечаниям → отметить исправления.

#### Функции

- Загрузка документа: PDF / DOCX / TXT / MD (минимум PDF + TXT для прототипа).
- Выбор типа документа и роли ревьюера (аналитик / разработчик / тестировщик).
- Кнопка «Запустить анализ».
- Просмотр исходного текста / структуры разделов (хотя бы plain text extract).
- Лента карточек замечаний с прожаркой и фильтрами.
- Действия по карточке:
  - **Исправлено** — пользователь подтверждает, что внёс правку в документ (или в локальный текст).
  - **Отклонено** — ложное срабатывание / неактуально.
  - **В работе** — опционально.
- Локальное редактирование текста документа в прототипе (textarea) — желательно, чтобы можно было «внести правку» без внешнего Word.
- Повторный анализ (re-run) после правок — nice to have.

#### UX-правила

- Сначала Well done / Medium, Rare не прячем, но можно свернуть.
- Карточка не должна быть «стеной текста»: проблема → вопросы → рекомендация.
- Видно, сколько замечаний в каждой прожарке (счётчики-светофор).

### Страница 2 — Дашборд самообучения аналитика

**Цель:** показать, где аналитик систематически ошибается, а где стабильно силён; дать рекомендации «тренировки».

#### Источник статистики (жёсткое правило)

В статистику попадают **только правки со статусом «Исправлено»**  
(т.е. замечания ИИ, которые аналитик реально принял и закрыл).

Не учитывать:

- отклонённые замечания;
- просто показанные / просмотренные;
- автозакрытие без действия пользователя.

#### Виджеты дашборда (минимум)

1. **Топ проблемных блоков**  
   Блоки шаблона с наибольшим числом исправленных замечаний (и/или суммарным score).  
   Текст: «В этих блоках ты чаще всего допускаешь пробелы…».
2. **Сильные стороны**  
   Блоки, где замечаний мало или score низкий при достаточном числе документов.  
   Текст: «Здесь ты заполняешь идеально / стабильно хорошо».
3. **Распределение по прожарке**  
   Well done / Medium / Medium rare / Rare среди принятых правок.
4. **Динамика** (если есть несколько сессий)  
   Число исправленных замечаний по датам / документам.
5. **Рекомендации самообучения**  
   3–5 пунктов на основе топа ошибок  
   (например: «Перед сдачей сверь Kafka-топики по всем регионам с таблицей приёмников»).

Хранение в прототипе: локальный `sqlite` / JSON / `st.session_state` + файл на диске. Схема должна быть легко переносима на бэкенд.

## 8. Мультиагентность (контракт для бэка, mock в прототипе)

Целевая архитектура — несколько агентов. В прототипе — **единый оркестратор + имитация ролей**.

| Агент | Фокус |
|-------|--------|
| Agent Analyst | полнота бизнес-описания, метрики, FAQ, заказчики |
| Agent Developer | источники/Kafka/кластеры, поля, SQL/логика, обновление |
| Agent QA | тестируемость: фильтры, граничные условия, объёмы, регламент, противоречия |
| Agent Risk Scorer | считает P, Impact, прожарку; может переранжировать |
| Agent Coach (дашборд) | агрегаты самообучения, тексты похвалы/рекомендаций |

Прототип может вызывать одну лёгкую модель с разными system prompts **или** rule-based генератор карточек по чеклисту шаблона. Интерфейс к модели — **абстракция** `LLMClient`, чтобы бэкенд/ML подменили endpoint без переписывания UI.

### 8.1. Лёгкая модель для прототипа

Допустимо:

- локальная лёгкая модель (например, через Ollama: `qwen2.5:3b` / `llama3.2:3b` / аналог);
- или облачный cheap API;
- или **полностью mock** (детерминированные замечания по regex/чеклисту) + 1–2 «живых» ответа модели для демо.

Требование: при отсутствии модели UI не падает — показывает mock-результат и баннер «LLM offline / demo mode».


## 10. Нефункциональные требования к прототипу

- Запуск: `streamlit run app.py` (+ `requirements.txt`, короткий README).
- Время анализа демо-документа: целевое < 60–90 сек; для mock — < 5 сек.
- Русский UI.
- Код без жёсткой привязки к конкретному провайдеру LLM.
- Логирование запросов/ответов модели в файл (для отладки бэком) — желательно.
- Не хранить секреты в репозитории (`.env.example`).

## 11. Out of scope (явно не делаем в прототипе)

- Учёт особенностей **разных команд-потребителей ТЗ** — идея масштабирования, только пометка в бэклоге.
- Прод-авторизация, SSO, RBAC.
- Интеграция с Confluence / Jira write-back.
- Автоматическое внесение правок в исходный PDF.
- Обучение/дообучение моделей, RAG на всём корп. контуре.
- Сравнение версий документов (можно в бэклог).

## 12. Критерии приёмки прототипа

1. Есть 2 страницы Streamlit: документ и дашборд самообучения.
2. Можно загрузить тестовый PDF из `ДатасетТЗ` и получить список замечаний.
3. Замечания покрывают (хотя бы частично) 4 фокус-зоны из §4.
4. У каждого замечания: проблема, вопросы, рекомендация, score, светофор, прожарка.
5. Можно отфильтровать по прожарке.
6. Статус «Исправлено» создаёт learning-событие; «Отклонено» — нет.
7. Дашборд показывает проблемные/сильные блоки на основе только исправленных.
8. Есть режим работы без модели (mock).
9. Описаны JSON-контракты и точки расширения под мультиагентный бэкенд.
10. На документе типа «витрина-агрегат» демо выглядит убедительно для передачи команде.

## 13. Метрика успеха продукта (качественная)

Не «количество замечаний», а **полезность указания на дополняемые места**:

- замечание привязано к конкретному блоку;
- понятно, *что* не так;
- есть путь к исправлению (вопросы + рекомендация);
- критичное не теряется среди шума (прожарка / светофор).

Для хакатона / демо: экспертная оценка «насколько попали в реальные дыры» на новом документе витрины-агрегата.

## 16. Решение по спорным UX-формулировкам (зафиксировано)

| Тема | Решение |
|------|---------|
| Приоритезация | `P × Impact` |
| Визуал важности | Светофор + прожарка |
| Лейблы прожарки | Well done / Medium / Medium rare / Rare |
| Статистика обучения | Только статус «Исправлено» |
| Командные особенности | Out of scope прототипа |
| Модели | Абстракция + лёгкая/mock; тонкая настройка — не наша зона |
