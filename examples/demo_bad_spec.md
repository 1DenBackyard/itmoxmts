# Техническое задание: витрина активности абонентов

## 1. Назначение

Необходимо создать витрину `dm_subscriber_activity`, содержащую актуальную информацию об активности абонентов мобильной сети. Витрина используется для ежедневной отчётности и расчёта маркетинговых показателей.

Заказчик: департамент маркетинга.  
Ответственная команда: Data Platform.

## 2. Источники данных

| Источник | Описание | Периодичность |
|---|---|---|
| `raw.calls` | Голосовые вызовы | ежедневно |
| `raw.data_sessions` | Сессии мобильного интернета | ежедневно |
| `customers` | Данные об абонентах | не указано |

Данные о регионе берутся из справочника базовых станций. Название справочника и ответственный за него не определены.

## 3. Состав витрины

| Поле | Тип | Описание |
|---|---|---|
| `report_date` | date | Дата отчёта |
| `subscriber_id` | string | Идентификатор клиента |
| `region_name` | string | Регион абонента |
| `calls_count` | integer | Количество звонков |
| `traffic_mb` | decimal(18,2) | Использованный интернет-трафик |
| `activity_score` | decimal(10,2) | Итоговый показатель активности |
| `is_active` | boolean | Признак активного абонента |

В источнике `raw.calls` идентификатор называется `msisdn`, а в `raw.data_sessions` — `subscriber_key`. Правила преобразования этих полей в `subscriber_id` не описаны.

## 4. Правила расчёта

1. `calls_count` — количество всех звонков абонента за отчётный день.
2. В другом отчёте необходимо учитывать только успешные исходящие звонки продолжительностью больше 5 секунд.
3. `traffic_mb` рассчитывается как сумма использованного трафика, поделённая на 1024.
4. Единица измерения исходного поля трафика не указана.
5. `activity_score = calls_count * 0.4 + traffic_mb * 0.7`.
6. Значение `activity_score` не должно превышать 100.
7. Правило ограничения значения до 100 не определено.
8. Абонент считается активным, если `activity_score` достаточно высокий.
9. Для клиентов без активности поля `calls_count` и `traffic_mb` заполняются нулями.
10. Клиенты без событий за отчётный день в витрину не загружаются.

## 5. Загрузка данных

Витрина обновляется инкрементально каждый день в 06:00 по московскому времени.

При повторном запуске выполняется полная перезагрузка данных за текущий месяц. Исторические записи удалять нельзя. Механизм защиты от дублей не описан.

Опоздавшие события должны учитываться, но допустимая глубина опоздания и порядок перерасчёта прошлых дат не заданы.

Ожидаемый объём — около 10 миллионов строк. Неизвестно, является ли это объёмом за день или общим размером витрины. Требования к времени выполнения отсутствуют.

## 6. Контроль качества

- Витрина должна содержать корректные данные.
- Количество строк должно примерно совпадать с источником.
- Дубли недопустимы.
- Состав бизнес-ключа не указан.
- Допустимое отклонение количества строк не определено.
- Правила обработки `NULL`, отрицательного трафика и неизвестного региона отсутствуют.

## 7. Ошибки и повторные запуски

При недоступности одного из источников процесс должен продолжить работу. При этом витрина должна содержать полные данные за отчётный день.

Не описано, что делать при частичной записи данных, повторной доставке одного события или изменении записи в источнике задним числом.

## 8. Приёмка

Результат считается принятым, если витрина создана и данные выглядят корректно. Конкретные тестовые сценарии, ожидаемые результаты и ответственный за приёмку не указаны.
