# ТЗ: прототип «Прожарка документации»

**Статус:** соответствует текущему HTML-прототипу  
**Стек:** чистый HTML / CSS / JS (без Streamlit, без бэкенда)  
**Запуск:** `cd web && python3 -m http.server 8080` → http://127.0.0.1:8080  

Вне скоупа прототипа: продакшен-инфра, боевая LLM, SSO, интеграция с Confluence/Jira, особенности разных команд-потребителей ТЗ.

---

## 1. Цель

Прототип UI и UX-потоков, который:

1. Анализирует документацию объектов данных (ТЗ).
2. Показывает замечания с приоритетом (прожарка / светофор).
3. Помогает исправлять: вопросы, рекомендация, кнопка **ИИсправь**.
4. Даёт итог ревью и выгрузку документа (PDF / текст) **с сохранением таблиц**.
5. Собирает **самообучение аналитика** («Мой прогресс») на подтверждённых замечаниях.

Анализ в прототипе — **демо-логика** (датасет + правила). Мультиагентная LLM — зона бэкенда; UI готов как эталон экранов.

Данные в датасете обезличены.

---

## 2. Пользователь

Основной пользователь — **аналитик**: загружает или создаёт ТЗ, проходит замечания, правит, отмечает статусы, смотрит прогресс обучения.

Отдельный переключатель ролей «аналитик / разработчик / QA» в текущем прототипе **не используется** (убран: мешал сценарию). Фокус ревью задаётся типом документа и фильтрами серьёзности.

Авторизация не нужна.

---

## 3. Входные данные

Папка: `ДатасетТЗ/`

| Файл | Назначение |
|------|------------|
| `Шаблоны документации.pdf` | Эталон структуры разделов |
| `Тестовые данные для Хакатона-2-4.pdf` | Потоки данных |
| `Тестовые данные для Хакатона-5-6.pdf` | Система-источник |
| `Тестовые данные для Хакатона-7-9.pdf` | Витрина-агрегат |

В приложении тексты и замечания лежат в `web/data/dataset.json` (собирается скриптом `web/scripts/build_dataset.py`).

### 3.1. Типы документов

1. Описание потоков данных  
2. Описание данных системы-источника  
3. Описание витрины-агрегата  

### 3.2. Блоки шаблона

Замечания маппятся на разделы шаблона (общие сведения, источники/приёмники, алгоритм, структура полей, регламент обновления и т.д.). Пустые обязательные блоки для выбранного типа ТЗ подсвечиваются как пробелы.

---

## 4. Фокус качества анализа

В первую очередь:

1. Источники и Kafka-кластеры (топики, кластер, путь, retention).  
2. Поля и логика расчёта (формулы, join, fallback).  
3. Фильтрация (условия, окна, исключения, NULL).  
4. Обновление и объёмы (регламент, инкремент/full, глубина, latency).  

Дополнительно: пустые обязательные секции, плейсхолдеры, противоречия между блоками.

---

## 5. Приоритет замечаний

```
score = P(проблема) × Impact
```

| Score (ориентир) | Светофор | Прожарка | Смысл |
|------------------|----------|----------|--------|
| ≥ 0.75 | красный | **Well done** | Критично |
| 0.45–0.74 | оранжевый | **Medium** | Существенно |
| 0.25–0.44 | жёлтый | **Medium rare** | Желательно |
| < 0.25 | зелёный | **Rare** | Незначительно |

В фильтрах старта и «Мой прогресс» пользователь выбирает три независимых уровня (можно несколько):

- Rare · Незначительные *(включает rare и medium_rare)*  
- Medium · Существенные  
- Well Done · Критические  

По умолчанию включены **все**. Фильтры меняют отображение, а не «глубину» проверки.

---

## 6. Карточка замечания

Обязательные поля:

1. **Проблема** — что не так.  
2. **Детали и вопросы** — 2–5 наводящих вопросов + рекомендация.  
3. **Метаданные** — блок, прожарка, статус, стабильный номер.  
4. **Якорь** — фрагмент текста в документе (подсветка + номер).  

Действия на карточке:

| Кнопка | Поведение |
|--------|-----------|
| 🔍 (лупа) | Найти фрагмент в тексте документа |
| **ИИсправь** | Показать diff «было → станет», по подтверждению применить к тексту |
| **Исправлено** | Статус `fixed` |
| **Отклонить** | Статус `rejected` |

Нумерация замечаний **не сбрасывается** при фильтрах и перепроверке.

---

## 7. Экраны прототипа

Поток: **Старт → Ревью → Итог**; отдельно **Мой прогресс**.

### 7.1. Старт

1. Выбор типа ТЗ.  
2. Способ начала:
   - **Создать с нуля** — каркас шаблона, сразу режим редактирования;
   - **Подгрузить своё ТЗ** — только **PDF** (таблицы извлекаются и рисуются как таблицы).  
3. При загрузке PDF — мультивыбор серьёзности (см. §5), все включены по умолчанию.  
4. Кнопка **Начать ревью**.

Эталон из датасета подключается, если имя загруженного файла совпадает с файлом в датасете (тогда берутся размеченные таблицы и замечания).

### 7.2. Ревью

Двухколоночный layout «как в Word»:

- **Слева** — документ (секции, markdown-таблицы → HTML-таблицы, подсветка якорей).  
- **Справа** — лента замечаний.  

Шапка ревью:

- счётчики: критичные / открыто / принято;  
- **Редактировать** — правка текста в том же листе;  
- **Сохранить и перепроверить** / **Перепроверить**;  
- **К итогу**.  

Фильтры замечаний: «Сначала критичные» / «Все открытые» / «Закрытые».  
Прогресс-бар: закрыто / всего по выбранной серьёзности.

### 7.3. Итог

- Сводка: принято / отклонено / ещё открыто.  
- Списки исправленного и оставшегося.  
- **Скачать PDF** — печать в PDF с HTML-таблицами.  
- **Скачать текст** — plain text черновика.  
- Переход в **Мой прогресс** / новый документ.

### 7.4. Мой прогресс (самообучение)

**Цель:** замечать повторяющиеся ошибки, разбирать их, накапливать чек-лист для следующих ТЗ.

Подзаголовок: «Учитесь на своих проверках: находите закономерности и улучшайте следующие ТЗ».

#### Фильтры

- Период: всё время / 30 / 90 дней.  
- Тип документа: все / потоки / источник / витрина.  
- Серьёзность: Rare / Medium / Well Done (мультивыбор, по умолчанию все).

#### Краткая сводка

- Проверено ТЗ (уникальные документы; повторная проверка того же ТЗ не увеличивает счётчик).  
- Подтверждено замечаний.  
- Исправлено замечаний.  

Исправления **не** считаются главным показателем обучения: прогресс — снижение повторяемости в **новых** документах.

#### Фокус на следующем ТЗ

До 3 карточек по повторяющимся **подтверждённым** ошибкам (≥ 2 разных ТЗ).  
Приоритет: сначала критичные, затем более частые.  
Кнопки: **Разобрать пример**, **Добавить в чек-лист**.

#### Мои повторяющиеся ошибки

Два вида: **по категориям** / **по смысловым блокам ТЗ**.  
Раскрытие строки → список замечаний → **Разобрать**.

Категории: Неполнота, Неоднозначность, Противоречия, Ошибки логики и расчётов, Непроверяемость, Нарушения оформления и терминологии.  

Смысловые блоки: цель и границы; источники и структура; потоки и загрузка; преобразования и расчёты; качество данных и исключения; результат и приёмка; иначе — «Не определён».

#### Разбор на моём примере (боковая панель)

1. Где найдено  
2. Исходный фрагмент  
3. Что не так  
4. Чем грозит  
5. Как исправить *(не применяется к документу автоматически)*  
6. Что запомнить  

Действия: подтвердить / не согласен (причина опционально) / отметить исправленным / добавить правило в чек-лист.  
Отклонённые **не** участвуют в персональных выводах.

#### Чек-лист перед отправкой ТЗ

Личные вопросы самопроверки. Можно добавить из разбора или вручную (без дублей), править, удалять, отмечать выполненным.  
**Начать проверку нового ТЗ** — сбрасывает отметки, пункты сохраняет, ведёт на Старт.

#### Состояния

- Нет проверок → «Загрузите первое ТЗ…»  
- Нет подтверждённых → призыв подтвердить замечания  
- Один документ → разбор и чек-лист есть, без выводов о повторяемости  
- Пустой срез фильтров → сброс фильтров  
- Нет повторов → нейтральное сообщение (не «гарантия качества»)

В прототипе страница наполнена **демо-данными** (`web/data/learning.json`), явно помеченными как демонстрационные.

**Не в первом прототипе:** рейтинг аналитиков, «балл профессионализма», курсы/тесты, график без истории.

## 8. Мультиагентность (контракт для бэка)

В UI агенты не выбираются. Целевая схема для бэкенда:

| Агент | Фокус |
|-------|--------|
| Analyst | полнота бизнес-описания |
| Developer | Kafka, поля, логика, обновление |
| QA | проверяемость, границы, противоречия |
| Risk Scorer | P, Impact, прожарка |
| Coach | агрегаты самообучения, рекомендации |

Прототип: mock / rule-based. Подмена на LLM — через будущий API без ломки экранов.

## 9. Контракты данных

### 9.1. Finding (ревью документа)

```json
{
  "id": "f_001",
  "doc_id": "doc_agg_01",
  "doc_type": "aggregate_mart",
  "block": "Алгоритм расчёта",
  "block_id": "algorithm",
  "anchor": { "excerpt": "…" },
  "problem": "…",
  "guiding_questions": ["…"],
  "recommendation": "…",
  "probability": 0.8,
  "impact": 0.9,
  "score": 0.72,
  "doneness": "medium",
  "traffic_light": "orange",
  "status": "open",
  "no": 3,
  "kind": "content"
}
```

`doneness`: `well_done | medium | medium_rare | rare`  
`status`: `open | fixed | rejected`  
`no` — стабильный номер в UI.

### 9.2. Learning finding (Мой прогресс)

Дополнительно к базовым полям:

- `topic_key` / `topic_title`  
- `category`, `semantic_block`, `tags[]`  
- `section_title`, `excerpt`, `highlight`  
- `explanation`, `impact`, `fix_suggestion`, `checklist_rule`  
- `confirm_status`: `proposed | confirmed | rejected`  
- `fix_status`: `open | fixed`  
- `doc_id`, `check_version`, даты проверки документа  

Повторная проверка, не породившая новое замечание, не создаёт новую ошибку в статистике.

## 11. Нефункциональные требования

- Русский UI.  
- Работа без серверного бэкенда (статический хостинг + `http.server`).  
- PDF-загрузка и таблицы работают в современном браузере.  
- При отсутствии модели / API UI не падает (только mock).  
- Секреты в репозиторий не класть.

---

## 12. Out of scope

- Прод-авторизация, SSO, RBAC.  
- Write-back в Confluence / Jira.  
- Автоправка исходного PDF «на месте» без явного подтверждения diff.  
- Обучение моделей / корп. RAG.  
- Рейтинг аналитиков и «балл профессионализма».  
- Учёт особенностей разных команд-заказчиков ТЗ.

---

## 13. Критерии приёмки (актуальный прототип)

1. Запуск через `web/` + локальный HTTP-сервер.  
2. Старт: тип ТЗ + с нуля / PDF.  
3. PDF: текст и таблицы отображаются в документе.  
4. При PDF — фильтр серьёзности (3 чекбокса, все on).  
5. Ревью: документ + замечания, якоря, стабильные номера, прогресс-бар, лупа.  
6. **ИИсправь** показывает diff и применяет после подтверждения.  
7. Исправлено / Отклонить меняют статус; перепроверка сохраняет закрытые.  
8. Итог: сводка + скачать PDF (таблицы) и текст.  
9. «Мой прогресс»: фильтры, сводка, фокус, повторы, разбор, чек-лист, демо-баннер.  
10. Нет Streamlit в поставке прототипа.

---

## 14. Метрика успеха

Не «число замечаний», а полезность:

- привязка к блоку и фрагменту;  
- понятно, что не так и как исправить;  
- критичное не тонет (прожарка + фильтры);  
- обучение строится на подтверждённых повторах, а не на «накликанных» исправлениях.

- Калибровка P/Impact по fixed vs rejected.
